# Isolated Tencent pilot deployment

Existing server: Ubuntu24.04, PostgreSQL16, meeting-assistant-public on5080,
Nginx443 with restricted allowlist. Never reinstall/upgrade/restart those services.

1. Run full tests, build web with `VITE_GRAYBOX_MODE=cloud`, then
   `node scripts/build-cloud.mjs`. Package ONLY `.local/cloud-release` contents.
2. On target, record meeting service main PID/start time and Nginx config checksums;
   back up Nginx config privately. Check no existing graybox users/roles/DB/paths.
3. Install official Node24.18.0 under `/opt/graybox/node`, no global PATH replacement.
   Linux x64 tar.xz SHA256: `55aa7153f9d88f28d765fcdad5ae6945b5c0f98a36881703817e4c450fa76742`.
4. Provision dedicated nonlogin Linux user graybox; separate graybox_cloud database,
   graybox_admin owner and graybox_runtime/graybox_auth login roles (NOSUPERUSER,
   NOCREATEDB, NOCREATEROLE, NOINHERIT). Runtime auth URLs must use these roles and
   target only graybox_cloud. Set role connection limits and SQL timeouts per role.
   Revoke public CONNECT on Graybox DB only; no changes to any existing database.
5. Run001+002 atomically as graybox_admin. Bootstrap owner invitation offline and
   save privately (24h, one-time); owner chooses their own username/password in UI.
   No production member passwords generated by automation or printed to logs.
6. Deploy immutable release under `/opt/graybox/releases/<release-id>`, root-owned,
   world-readable code/static only. `/opt/graybox/current` points to release.
   Secrets `/etc/graybox/runtime.env` root:graybox0640. Contains GRAYBOX_MODE=cloud,
   GRAYBOX_DATABASE_URL and GRAYBOX_AUTH_DATABASE_URL; admin credentials separate
   root-only migration.env. Use systemd unit, inspect localhost4318 health.
7. Install separate `graybox.nginx.conf`, `nginx -t`, gracefully reload Nginx only.
   Verify certificate hostname api.qingsuworks.top at8443, using --resolve locally.
   Domain DNS/certificate retained. HTTPS TLS origin differs by port and browser
   storage is memory-only. Do not expose4318/5432 or alter443 existing allowlist.
8. Open only8443 for selected team IPs or public authenticated pilot when explicitly
   authorized at the firewall step. Preserve existing22/443/80 rules.
   Check both Tencent firewall and host UFW; an active default-deny UFW needs the
   same narrow IPv4 TCP8443 rule. Do not disable UFW or broaden existing rules.
9. Record meeting service same PID/start, old443 HTTP status unchanged, resource caps,
   cloud login/pairing and shared records. Real second-device/team acceptance remains
   a separate user test. Isolated test accounts cannot count as real member acceptance.

Rollback: stop graybox.service, remove only its new Nginx enabled symlink after verifying
exact path, nginx -t and reload; close only the new firewall8443 rule. Retain all Graybox
data/releases/backups for recovery. Do not drop databases, reset old configuration or
stop shared PostgreSQL. Upgrade rollbacks must check migration compatibility first.

Run backup.sh as root; verify archive checksum/list, then restore into a separate
`graybox_restore_check` database and compare counts/revisions before saying restoration
is tested. A successful dump alone does not establish disaster recovery. Store an
encrypted off-host backup before treating the pilot as production-critical.

## Existing installation upgrade (project library 0.2)

Do not rerun install.py on the existing server. Build and checksum a new server archive,
upload it to a fresh root-private staging directory, and inspect its release metadata.
Run `python3 ops/test_upgrade.py` from the staged release before `python3 ops/upgrade.py`.
The upgrade script holds an exclusive operation lock, copies an immutable release,
checks Node syntax, stops only Graybox, runs the previous release's backup script,
then runs the reviewed migrations and old-data preservation guard in one transaction.
Only additive changes may commit. It switches the release pointer, starts Graybox and
checks HTTPS/environment identity, existing service PIDs and Nginx configuration hashes.
No invitation, account, credential, firewall, Nginx or shared PostgreSQL changes occur.

Migration SQL is trusted reviewed source. Do not put independent BEGIN/COMMIT or
nontransactional operations inside migration files. The guard verifies old table rows,
including nested JSON and array values, before COMMIT; it is not a SQL sandbox.

Upgrade reports and pre-migration snapshots remain root-private under
`/var/lib/graybox/upgrade-*.json`; snapshots can contain authentication hashes and must
not be published. On failure the script separately attempts stop, restore old pointer,
start and old-environment health verification, and reports whether recovery succeeded.
Backups, old/new releases and additive schema are retained. It never restores a database
automatically or destroys later user writes. The old UI cannot access new library fields;
after any manual downgrade, pause writes until compatibility is assessed. Actual restore
testing and real friend-device acceptance are separate checks from a successful upgrade.


## 0.5 附件升级

既有安装先执行新发布包中的 `python3 ops/configure-attachments.py`，再执行新包的 `bash ops/backup.sh` 和 `python3 ops/upgrade.py`。准备脚本只修改 Graybox 的 8443 站点、服务单元和运行环境，保留配置私有备份并核对原有 443 项目和 PostgreSQL。普通 upgrade.py 仍要求 Nginx 在它执行期间不变。

附件持久化在 `/var/lib/graybox/attachments`，由 Graybox 账号独占；服务只获得该目录写权限。默认团队额度 1 GiB，通过 `GRAYBOX_ATTACHMENT_QUOTA_BYTES` 调整。备份是数据库 dump、附件 tar 和同名 manifest 的一对；恢复时必须一起使用，私有备份不上传公开仓库。备份仍需另行复制到其他设备以应对服务器丢失。

图片 10 MiB、视频 50 MiB、单 HTML 5 MiB。上传路由单独允许 50 MiB，其他 API 保持 256 KiB。HTML 预览使用 60 秒授权入口，每次重新核对凭据与目标权限；沙箱仅允许内联脚本，不允许外部请求或父页面访问。
